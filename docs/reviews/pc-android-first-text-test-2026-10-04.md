# Первая ручная проверка ПК ↔ Android

Это инструкция для первого неизменяемого Direct-текста. Физическая проверка ещё не выполнена. Файлы EXE/APK и их контрольные суммы выдаются только после завершения сборки и проверки артефактов; текущий статус находится в [журнале реализации](reliability-implementation-2026-10-04.md).

## Подготовка

Используй два разных аккаунта, по одному устройству на каждом. Не восстанавливай на телефоне фразу аккаунта с ПК: поддержка одного аккаунта на двух устройствах этим тестом не проверяется. Для отдельного тестового аккаунта на ПК можно использовать отдельного пользователя Windows; обычный desktop EXE использует существующее хранилище текущего пользователя.

На телефоне устанавливается **Veil Tester**, пакет `io.veil.mobile.tester`. Он имеет собственное хранилище и сосуществует с `io.veil.mobile`. Если Android сообщает о конфликте подписи уже установленного tester, остановись и сообщи об этом; не удаляй приложение и не очищай данные для обхода ошибки.

Адрес Node: `https://veil.erez.pro`. На ПК соответствующие endpoints — `wss://veil.erez.pro/v3/events` и `https://veil.erez.pro`. На телефоне укажи HTTPS origin без пути. Отдельного файла witness-настроек для первого теста не требуется. Этот режим не доказывает проверку внешними witnesses; ранее закреплённые настройки доверия нельзя сбрасывать.

На 2026-10-04 read-only проверка Node показала `/health` → `ok`, опубликованный source revision — `6c0ff0561547d4fe6e8665203f7e5841b5447b64`. Локальные серверные исправления этой работы ещё не развёрнуты на Node. Успех совместимости проверяется вручную, а не выводится из состояния health.

## Вход и подключение

1. Запусти выданный EXE. Если аккаунт уже существует, разблокируй его; не выбирай сброс или замену identity. Для нового аккаунта пройди создание и запиши recovery phrase локально.
2. Установи выданный APK вручную и открой **Veil Tester**. Создай отдельную identity через защищённый native-экран, запиши и подтверди её recovery phrase локально.
3. Подключи оба клиента к указанному Node. Дождись завершения публикации prekeys, загрузки списка бесед и истории. Одного статуса сетевого соединения недостаточно.
4. Если показан `VEIL-PASS-001`, регистрация закрыта: нужен отдельный одноразовый Node Access Pass для каждой новой identity. Его выдаёт администратор существующего Node. На сервере используется `/app/veil-admin invite create --count 2 --expires 24h`; выполнять команду нужно в окружении действующего Node с его настройками БД. Не открывай регистрацию всем ради теста.
5. Для телефона открой свою HTTPS-ссылку Pass в браузере и нажми на странице **«Скопировать ссылку»**. Вернись в tester и нажми **Import invitation from clipboard**. Проверь показанный origin и примени Pass. Native-код читает токен по явному нажатию; React получает только безопасный reference и время действия. Кнопка обычного сайта «Открыть Veil» относится к основной схеме `veil://` и не предназначена для tester. После импорта буфер остаётся до твоего следующего копирования или очистки.
6. Для ПК используй предусмотренный импорт Access Pass в desktop GUI. Токен, полную ссылку и recovery phrase не присылай в чат и не включай в отчёт.

Постоянный tester-ключ сохранён вне репозитория в `C:/Users/Dimon/.veil-private/android-tester-signing`. Сохрани защищённую резервную копию этой папки: тот же ключ необходим для будущих обновлений tester. Production-сертификат пока не создан; текущий tester квалифицируется по отдельному bootstrap-контракту, а не как production release.

## Первый обмен

1. На телефоне открой **Find someone**, найди точный username аккаунта ПК, выбери результат и создай Direct. Дождись открытия настоящей беседы.
2. Отправь только с телефона `PHONE-01: привет, ёж 🦔`. На ПК дождись получения и проверь точный текст.
3. Только после получения на ПК ответь `PC-01: ответ получен ✅`. На телефоне проверь точный текст и одну строку сообщения.
4. Повтори по одному сообщению с каждой стороны. `Sent` означает принятие Node, а не прочтение собеседником. Ожидающее сообщение не должно получать выдуманное время.
5. Проверь возврат в Home и повторное открытие беседы, ввод длинного текста, клавиатуру и доступность кнопки отправки. При блокировке/уходе в фон plaintext должен закрываться защищённым экраном; после возвращения выполни явное разблокирование, если его требует приложение.

**Не отправляй первые сообщения одновременно.** Отдельная регрессия фиксирует существующую проблему crossed INITIAL: две независимо начатые сессии могут остаться несовместимыми. Первая последовательная проверка не закрывает этот дефект. Не пытайся исправить такой исход удалением локальных сообщений или сбросом ratchet.

В первом сценарии не используй TTL, reply, вложения, edits/deletes и группы. Проверки offline compose, полного catch-up, push и нескольких устройств проводятся отдельно после соответствующих native-контрактов. Не удаляй приложение и не отключай сервер во время первого обмена.

## Что сообщить по результату

Достаточно модели телефона/версии Android, версии выданных файлов, этапа сбоя и публичного кода ошибки, а также наблюдений: найден ли контакт, создана ли беседа, дошёл ли текст в каждом направлении, появились ли дубли, перекрывает ли клавиатура ввод. Не присылай recovery phrase, Pass, базу данных или полный лог.

Дальнейшая матрица сбоев и восстановления находится в [physical test plan](android-direct-preview-physical-test-plan.md). Этот короткий обмен подтверждает только наблюдаемый text-сценарий и не заменяет всю матрицу.
